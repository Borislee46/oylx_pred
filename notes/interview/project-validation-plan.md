# 项目验证实验计划

> 目标：用留学预测项目产出真实数据证据，让面试回答从"我学过"变成"我验证过"
> 原则：每个实验产出两样东西——(1) 一张可放进 portfolio 的图/数字 (2) 一个可被追问 3 层的面试答案
> 时间：12 个月，按优先级分批

---

## 分类体系

| 类别 | 定义 | 面试姿态 |
|------|------|---------|
| **V** (Validate) | 项目数据能严格验证 | "我做过，这是数据" |
| **S** (Simulate) | 不能做真的，但能用历史数据模拟 | "我模拟过，知道结论和局限" |
| **H** (Honest) | 项目条件不允许，但知道理想做法 | "我知道边界在哪，规模允许时我会..." |

---

## 第一层：V — 现在就能验证的（数据已有）

### V1. 校准深度分析

**为什么重要**：你已经在简历上写了 sigmoid calibration。面试官追问"校准前后 Brier 差多少"时，你要报出精确数字。

**实验**：
```
1. 在测试集上收集 calibration 前的 raw XGBoost 预测概率
2. 收集 calibration 后的概率
3. 画 reliability diagram（校准前 vs 校准后，两条线叠在同一张图上）
4. 计算：Brier Score 分解 = Calibration - Refinement + Uncertainty
5. 计算 ECE (Expected Calibration Error)，分 10 个 bin
6. 标注：校准前在低概率段（0-20%）模型是系统性高估还是低估
```

**当前数据**：Brier=0.185，predicted_positive_rate=54.9% vs actual=33.7% → **模型整体高估了 ~21%，校准没有完全修正**。这是个值得深挖的发现。

**面试答案**：
> "我校准前 Brier 是 X，校准后是 Y，降了 Z%。但有个有意思的发现——即使在 sigmoid 校准后，模型在低概率段（0-20%）仍然系统性高估了约 15%。这可能是校准集本身也有选择偏差，因为我用的是随机 20% holdout，而不是时间上最近的样本。如果用最近一季度的录取结果做校准集，效果可能更好。"

**产出**：1 张 reliability diagram + 1 个 Brier 分解表

---

### V2. 五层调整链 Ablation Study

**为什么重要**：面试官最常追问的就是"你怎么证明每层都有必要"。

**实验**：
```
baseline = 完整 5 层 pipeline 的 top-20 推荐排序
对每一层：
  ├── 关掉该层 → 跑同样 200 个 case → 得到新排序
  ├── 计算 Kendall's tau vs baseline（排序一致性）
  ├── 计算 top-5 / top-10 推荐列表重叠率
  └── 标注该层影响最大的 3 个 case（最大排序变化的 case）
```

**关键洞察**：不同层的 Kendall tau 会非常不同：
- 跨专业惩罚层（×0.5）→ 对排序影响最大（tau 可能 < 0.8）
- GPA 惩罚层 → 对低 GPA 学生影响最大，对高 GPA 学生几乎无影响
- 文本提升层 → 对有强出版物/科研的少数学生影响集中

**面试答案**：
> "我做了完整的 ablation——每关掉一层，看 top-10 推荐的 Kendall tau 变化。跨专业惩罚层对排序影响最大（tau=0.72），因为它直接改变了跨专业申请的可行性判断。GPA 惩罚层 tau=0.91，整体影响小但对低 GPA 尾部学生（<2.5）影响显著。这说明五层各有分工：有的做全局约束，有的做局部修正。"

**产出**：1 张 ablation 矩阵图 + 每层 1 个最极端 case 的 trace

---

### V3. 阈值敏感性分析（Cost-based Threshold）

**为什么重要**：你目前 threshold=0.24 是 F1 最优，但 F1 假设 FP 和 FN 代价相等。

**实验**：
```
定义 cost ratio r = cost_FP / cost_FN
r=0.5 → "漏掉机会比推荐错更严重"（宁可多申）
r=2.0 → "推荐错比漏掉更严重"（精确优先）
r=1.0 → 等于 F1 最优

对 r ∈ {0.2, 0.5, 1.0, 2.0, 5.0}：
  └── 计算最优 threshold、对应的 precision/recall、净 cost
```

**面试答案**：
> "我目前的 threshold=0.24 是 F1 最优，但 F1 假设 FP 和 FN 代价相等。我做了 cost-sensitive 分析——如果业务方认为'推荐错一个不该申的学校'代价是'漏掉一个能申的'的 2 倍，最优 threshold 应该从 0.24 调到 0.31，precision 从 48% 升到 56%，但 recall 从 78% 降到 64%。这个 tradeoff 应该由业务方拍板，不是我从 F1 推导。"

**产出**：1 张 cost-threshold-precision-recall 三轴图

---

### V4. 特征重要性稳定性（Bootstrap）

**为什么重要**：单次特征重要性排序可能不稳定。面试官问"你确定 target_major 真的最重要吗"时，你要有置信区间。

**实验**：
```
bootstrap 1000 次（有放回采样训练集）：
  ├── 每轮训练一个 XGBoost（简化参数，快速训练）
  └── 记录每个特征的重要性排名

输出：
  ├── 每个特征排名的 95% CI（如 target_major: rank 1-3, 95% CI）
  ├── 排名最稳定的特征（如 gpa 始终 top-3）
  └── 排名最不稳定的特征（如 paper_count 在 3-7 之间跳动）
```

**面试答案**：
> "我做了 bootstrap 特征重要性分析——target_major 和 background_university 的 top-2 地位非常稳定（95% CI 分别是 rank 1-3 和 1-4），但 paper_count 和 internship_count 的排名高度重叠（CI 交叉），不能严格说谁更重要。这对 feature selection 有实际指导——如果要砍特征，论文和实习可以二选一。"

**产出**：1 张 bootstrap 特征排名箱线图

## 第二层：S — 可以模拟的（用历史数据构造）

### S1. Rolling Window Backtest（模拟时间验证）

**为什么重要**：你现在的评估是随机 split，但这不能回答"模型在持续运营中稳不稳定"。

**实验设计**：
```
如果数据有时间戳（录取年份/申请年份）：
  window_size = 最近 2000 例
  窗口 1: train on 最早 2000 例 → test on 接下来 500 例
  窗口 2: train on 接下来 2000 例 → test on 再接下来 500 例
  ...滚动 10 个窗口

  追踪每个窗口的：AUC, Brier, precision, recall, positive_rate_bias
  → 画一条时间趋势线，看是否有 drift
```

**如果没有时间戳**：
```
用不同年份的学校录取数据做 proxy：
  ├── train on 2023 入学 → test on 2024 入学
  ├── train on 2024 入学 → test on 2025 入学
  └── 比较跨年度的指标衰减
```

**面试答案**：
> "我用 rolling window backtest 模拟了时间验证——把数据按录取年份切分，用早期数据训练、近期数据测试。AUC 从最早窗口的 0.76 降到最后窗口的 0.72，Brier 从 0.18 升到 0.20，说明有轻微 concept drift。这让我知道模型大约需要每 6-12 个月 retrain 一次。目前训练脚本是手动的，如果规模大了我会加 automated retrain trigger。"

**产出**：1 张 rolling window 趋势图（指标 vs 时间窗口）

### S2. Peeking Problem 模拟（统计教育工具）

**为什么重要**：面试必考题。你说"我知道 peeking 会膨胀 Type I Error"，但如果你能说"我在自己数据上模拟过，膨胀了多少"，可信度差一个级别。

**实验设计**：
```
模拟场景：有一个"实验组"和"对照组"（实际上是从同一分布抽样的两组）
真正的 treatment effect = 0（没有区别）

场景 A（不偷看）：固定 N=2000，跑完才看 p 值
场景 B（每天偷看）：每 100 个样本看一次 p，p<0.05 就停
场景 C（每天偷看+分群）：每 100 样本看一次，还分男女/分学校层级各看一次

各重复 1000 次，统计：
  ├── Type I Error rate（实际 p<0.05 的比例）
  ├── 场景 A: ~5%（正常）
  ├── 场景 B: ~20-30%（膨胀！）
  └── 场景 C: ~40-50%（严重膨胀！）
```

**面试答案**：
> "我在自己项目数据上做了 peeking 模拟——从同一批学生中随机抽两组（实际没有差异），模拟'每天看一次 p 值'的实验习惯。不偷看时 Type I Error 确实是 5%，但每天偷看一次就膨胀到 ~25%，如果同时分男女、分学校层级各看一次，膨胀到 ~45%——意味着你有一半概率'发现'一个根本不存在的效果。这就是为什么我坚持提前算 MDE、固定样本量。"

**产出**：1 张 peeking 模拟图（横轴=样本量，纵轴=累积 Type I Error，三条线）

---

### S3. Multiple Testing 校正演示

**为什么重要**：跟 peeking 配套，展示你对多重比较的理解不只是背定义。

**实验**：
```
用真实特征数据，生成 20 个"假实验指标"（加随机噪声）
不做校正：p<0.05 → 预期 1 个假阳性
Bonferroni: p<0.05/20 → 0 个假阳性
Benjamini-Hochberg (FDR=0.1): 1 个假阳性但 power 比 Bonferroni 高

输出对比表：哪些指标在 raw p 下"显著"但在校正后不显著
```

**面试答案**：
> "我在项目里模拟过——如果用 20 个指标评估同一个策略且不做多重比较校正，纯靠运气就会有 1 个'显著'。Bonferroni 最保守但 power 低，Benjamini-Hochberg 更实用。这让我养成了一个习惯：实验前锁定主指标，探索性分析的结果标注'未经多重比较校正'。"

**产出**：1 张校正前后对比表

---

### S4. Power Analysis / MDE 计算

**为什么重要**：面试问"实验不显著怎么办"，标准答案是"算 MDE"。如果你用自己数据算过，可以报出精确数字。

**实验**：
```
基于你的数据：
  baseline conversion rate（如录取率 ~34%）
  当前样本量（如 ~12000 例）
  α=0.05, power=0.8

  计算 MDE：在当前样本量下，能检测到的最小 treatment effect 是多少？
  → 如：需要录取率从 34% 提升到 36.5%（相对提升 7.4%）才能被检测到

  反向计算：如果想检测 +2% 的录取率提升，需要多少样本？
  → 如：需要 ~50000 例（远超现有数据量）
```

**面试答案**：
> "我算过——以我当前约 12000 例的样本量，在 α=0.05, power=0.8 下，只能检测到约 +2.5pp 的录取率变化（从 34% 到 36.5%，相对 7.4%）。如果我想检测 +1pp 的细微提升，需要约 50000 例——这解释了为什么在教育场景下很难靠 AB 验证微调效果，也影响了我的评估策略：更依赖 calibration 和 holdout 而非线上 AB。"

**产出**：1 张 power curve（横轴=样本量，纵轴=MDE）

---

### S5. 分层采样效率演示

**为什么重要**：你在字节做过"实验样本特殊圈"，面试官会追问"分层到底提升了什么"。

**实验**：
```
用真实数据模拟：
  └── 按 school_tier（学校层级）分层
  ├── 简单随机分组：计算 treatment/control 在各层的 GPA 均值差异
  └── 分层随机分组：同样计算

比较两种方法的 variance reduction：
  → 分层后组间更均衡 → 方差更小 → 同样样本量检测力更高
```

**面试答案**：
> "我在自己数据上验证过——按学校层级做分层后，GPA 的组间差异减少了约 60%。这意味着同样 2000 样本，分层后能检测到的 MDE 比简单随机小约 15-20%。这也解释了为什么我在字节做实验时，Libra 默认按用户特征做分层——不是形式主义，是有统计学收益的。"

**产出**：1 张分层 vs 简单随机的组间均衡对比图

---

### S6. OOD 检测系统化

**为什么重要**：你在 Q&A 里答得不错（高分端透出、低分端 flooring），但面试官可能追问"你怎么系统化检测而不仅是依赖范围判断"。

**实验**：
```
基于训练数据：
  ├── 计算每个特征的一维分布（GPA 均值/std、语言成绩分布、各学校/major 出现频率）
  ├── 对新 case，标记哪些特征落在 [P2.5, P97.5] 之外
  ├── 统计：有多少 case 至少 1 个特征 OOD？2 个？3 个？
  └── 对比 OOD case 的模型预测 vs 最终录取 → 模型对 OOD case 的准确率是否显著更低？

建立 OOD flag 规则：
  ├── GREEN: 0 个特征 OOD → 正常预测
  ├── YELLOW: 1-2 个特征 OOD → 正常预测 + 标注 "部分依据有限"
  └── RED: 3+ 个特征 OOD → 仅依赖规则层，XGBoost 预测仅作参考
```

**面试答案**：
> "我给我的系统加了 OOD 分级——统计训练数据每个特征的分位数，对每个新 case 计数有多少特征落在 P2.5-P97.5 之外。0 个正常，1-2 个标黄'部分依据有限'，3+个标红'仅规则推断'。我发现约 12% 的 case 有至少 1 个 OOD 特征，但这些 case 的模型准确率确实显著更低（比 in-distribution 低了约 8 个点），验证了 OOD 检测的必要性。"

**产出**：1 张 OOD 分级准确率对比 + OOD 特征分布图

## 第三层：H — 不能验证但知道怎么做

这些是你的"诚实边界"——面试时坦诚说没做过，但能说出理想设计和现实约束的差距。

### H1. 真实线上 A/B 测试

**为什么不能做**：Streamlit 单机部署，没有流量分流能力。预测结果直接影响用户决策，不能随机给"差"推荐。

**面试姿态**：
> "目前在 Streamlit 单机部署下没法做流量分流，但我设计过实验方案：
> - 实验单元：顾问级别随机化（不能让同一顾问看到两个版本的推荐）
> - 主指标：推荐采纳率 + 最终录取率
> - 护栏指标：顾问满意度、学生投诉率
> - 最大挑战：self-fulfilling prophecy——系统不看好的组合永远不会被验证，需要 exploration arm
> - 如果我是这个系统的 DS lead，我会先用 holdback 验证（去年数据回测今年），再设计 low-traffic exploration arm 收集反事实数据。"

---

### H2. SRM (Sample Ratio Mismatch)

**为什么不能做**：没有真实实验分流。

**面试姿态**：
> "我在字节 Libra 面板上见过 SRM 检查，但自己的项目没有实验系统所以没做过。如果我设计实验平台，SRM 会是上线后的第一个自动检查——实验组/对照组比例偏离 50:50 超过 1% 立即告警，因为这通常意味着分流 bug、bot traffic 或 instrumentation 问题，比指标本身更紧急。"

---

### H3. CUPED

**为什么不能做**：没有 pre-experiment 用户行为数据。

**面试姿态**：
> "CUPED 的核心是用实验前指标做协变量降低方差。在录取预测场景下，自然的 pre-experiment 变量是学生的历史 GPA 和学校层级——如果我做顾问级别实验，可以在分析时把'顾问过去 3 个月的平均推荐采纳率'作为 CUPED 协变量，预期 variance reduction 约 30-50%。方法上我知道怎么实现——ANCOVA 框架，pre-experiment metric 做协变量——但项目规模还没到这个程度。"

---

### H4. Interleaving（交织实验）

**为什么不能做**：不是搜索系统，没有排序列表可以交织。

**面试姿态**：
> "Interleaving 是搜索/推荐领域比 AB 更敏感的评估方式——把两个排序结果交织成一个列表给用户，看哪个排序的 item 被点击更多。我这里不适用，但在字节搜索的经历让我知道：interleaving 的核心优势是 within-subject comparison（同一个人同时看到两个排序的结果），方差远小于 between-subject AB，样本量可以小 10-100 倍。代价是实现复杂——需要保证交织算法的公平性（Team Draft vs Balanced）。

---

### H5. Network Interference（网络干扰）

**为什么不能做**：没有社交图/用户互动数据。

**面试姿态**：
> "Network interference 发生在实验组用户影响对照组用户时——比如 LinkedIn 给实验组推送更多某类内容，实验组用户分享后对照组也看到了，导致对照组也被'间接 treatment'。我的场景下基本没有——顾问之间互相看不到对方的推荐，决策独立。但如果系统扩展到学生端（学生之间会讨论推荐结果），就需要考虑。解决方案是 cluster randomization（按学校/班级分组而非按个人），只是需要的样本量大很多。"

---

### H6. Sequential Testing & Alpha-Spending

**为什么不能做**：没有实时实验监控平台。

**面试姿态**：
> "Sequential testing 是 peeking 问题的正式解决方案——不是禁止中间看数据，而是通过 alpha-spending function 控制整体 Type I Error。O'Brien-Fleming 边界是最常用的：早期 interim 用极严格的 p 值门槛（如 p<0.001），最后几次放宽。我没在项目中实现过——目前连真实 AB 都没有——但我在 peeking 模拟中验证过：用 Pocock boundary（α=0.05 分 5 次看，每次门槛 0.015）代替 naive peeking，Type I Error 从 25% 降回了 ~5%。"

## 面试叙事的升级版（做完 V1-V4 + S1-S2 后）

做完这些实验后，你的 2 分钟项目介绍可以升级为：

> "我独立负责了一套留学录取预测系统，从训练到部署完整闭环。我做了 3 个系统性的验证：
> 1. **校准验证**：sigmoid calibration 后 Brier Score 从 X 降到 Y，但 reliability diagram 显示低概率段仍有 ~15% 高估——我定位到校准集的时间偏差，这是 rolling window backtest 才暴露的问题
> 2. **消融实验**：五层调整链每层独立关掉的排序变化——跨专业惩罚层对排序影响最大（Kendall tau=0.72），GPA 惩罚主要影响低分尾部
> 3. **统计意识**：我在项目数据上模拟了 peeking problem、多重比较校正、power analysis，知道如果规模允许，真实 AB 应该怎么做
>
> 系统现在线上每天被 N 个顾问使用。"

## 一个额外建议

你 S1-S6 这些模拟实验的代码，本身就可以作为你 GitHub 上的一个独立 repo 或子目录——叫 `experiment-simulations/`。这不只是帮你准备面试，本身就是一个"DS 实验思维"的 portfolio 作品。面试官看到一个人在没有 AB 平台的条件下，自己写模拟去验证统计概念，会比你背 Kohavi 书上的内容印象深刻得多。
