## 第一篇：XGBoost 层

**标题候选**：
- `传统机器学习过时了吗？传统行业如何利用 XGBoost + Agent 压缩成本到极致承载业务`
- `当你的业务有明确的先验知识，XGBoost 比 LLM 更可靠`
- `从 0 到 1 搭建可解释的录取预测系统：XGBoost 为什么是正确选择`

**核心论点**：
- 留学录取场景有明确的先验知识（GPA越高越好、经历越多越好）→ monotonic constraints 直接编码
- XGBoost 推理成本 ≈ 0，LLM/RAG 推理成本 ≈ 每次几毛~几块 → 批处理3000+学校组合的成本差异是数量级的
- 概率调整链（GPA/语言偏差惩罚 → 跨专业×0.5 → 跨学院×0.3 → TF-IDF提升）每一环都可辩护
- 校准（sigmoid Platt scaling, threshold=0.24）有统计依据

**叙事线**：
1. 问题：留学顾问需要快速评估学生能申哪些学校，"感觉"不可靠
2. 为什么不是LLM：成本、幻觉（不懂这个学校的录取偏好）、无法量化不确定性
3. XGBoost的设计决策：monotonic constraints、log1p变换、中位数填充、语言归一化——每个选择有理由
4. 概率调整链：模型输出不是终点，规则层编码业务专家知识
5. 效果 + 业务专家认同 = 投产

## 第二篇：Agent 层

**标题候选**：
- `当员工拒绝一步到位的 Copilot/Chatbot/Lobster 时，如何承前启后用轻量 ML 数据产品过渡`
- `Agent 不替代人：用两个轻量 Agent 把顾问从解释性劳动中解放出来`
- `从表单到自然语言：一个留学系统的 Agent 过渡策略`

**核心论点**：
- 员工拒绝"一步到位"的 Agent 产品是正常的——信任需要积累
- Agent 的正确切入口不是"替代顾问决策"，而是"替代解释性劳动"
- LeadInAgent：碎片文本 → 结构化背景（模糊匹配 + 多轮增量）
- ExplainAgent：预测结果 + 背景 → 自然语言解读（overview / strengths / concerns / summary）
- 三级 JSON 容错（直接parse → 正则修复 → API repair）是生产级Agent的工程细节

**叙事线**：
1. 问题：有了预测结果，顾问还是要花大量时间"解释"给学生听
2. 为什么不是ChatGPT直接解释：幻觉、不懂业务上下文、无法关联预测模型的内部逻辑
3. LeadInAgent：怎么把"学生是北大的、GPA 3.5、想申港大金融"这种碎片输入变成结构化表单
4. ExplainAgent：怎么让AI解读预测结果，同时保证每句话都有数据支撑
5. 工程细节：三级JSON容错、缓存策略、streaming输出——Agent在生产环境不是demo

## 第三篇：泛化/展示层

**方向A：系统泛化**

标题候选：
- `当模型不能泛化时，泛化系统：多源证据架构的设计决策`
- `你的训练数据有边界：为什么不把外部数据倒进XGBoost`

核心论点：
- XDF内部数据有分布边界，外部数据（ApplySquare全球论坛 + 指南者竞品）分布不同、bias不同
- 混入训练是危险的——模型可能学到数据源artifact而非录取规律
- 解法：模型不动，外部数据独立成证据层
- Multi-Source Evidence Architecture：P50画像（指南者） + 差异分析Cohen's d（ApplySquare）+ 相似案例检索
- 这不是模型泛化，是系统泛化——更可控、更可解释、零回滚风险

**方向B：从预测到决策**

标题候选：
- `从预测到决策：一个概率数字背后应该跟多少信息`
- `15%录取概率，然后呢？反推卡片与竞争画像的DS设计`

核心论点：
- 预测概率是一个数字，决策需要更多信息
- 反推卡片：翻转视角，从"你能进吗"到"学校喜欢什么样的学生"
- 竞争画像：同一目标学校，什么背景的人在跟你竞争
- 展示层设计哲学：不是给用户更多数字，是给用户正确的信息架构

```
              ↓
       统一主题：DS 不是在调参，是在做决策
```
